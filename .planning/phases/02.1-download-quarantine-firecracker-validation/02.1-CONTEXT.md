# Phase 2.1: Download Quarantine & Firecracker Validation - Context

**Gathered:** 2026-10-23
**Status:** Ready for planning

<domain>
## Phase Boundary

No downloaded file reaches the media folders (and so Jellyfin) unless a sandboxed probe proves it is a real video. Completed Film/SerieTV downloads land in a quarantine folder. Each file is probed with ffprobe inside a throwaway Firecracker microVM, and only passing files are handed to `media/Film` or `media/SerieTV`. Failing files are held out of reach and auto-purged, and their torrent is removed. The Downloads tab shows Checking… → Ready / Rejected. Requirements: QUAR-01..QUAR-05.

Not in this phase: renaming into Jellyfin's layout (Phase 4 adds it at the hand-off step), Jellyfin itself (Phase 3), TV-compatibility checks of codecs (Phase 3).

</domain>

<decisions>
## Implementation Decisions

### Host layout and hand-off
- **D-44:** One **`DATA_ROOT`** parent replaces the separate `MEDIA_ROOT` / `INCOMPLETE_DIR` roots: `DATA_ROOT/{media/Film, media/SerieTV, quarantine/Film, quarantine/SerieTV, rejected, incomplete}`. qBittorrent and the backend mount `DATA_ROOT` as **one** bind mount, so hardlinks work. Jellyfin (Phase 4) will mount only `media` read-only. `docs/ports-and-media.md`, `scripts/init-host-dirs.sh`, `.env.example`, compose and the infra tests are updated to match. — **Reversibility:** costly — changes the documented media contract, compose mounts, env names and infra invariant tests; the existing host folders must be moved by the admin.
- **D-45:** qBittorrent category save paths point at `quarantine/<Category>` (not media). Admin-added Film/SerieTV torrents go through the **same pipeline** (D-34 spirit); nothing bypasses the check.
- **D-46:** Passing files are **hardlinked** into `media/<Category>`, keeping the torrent's relative folder structure minus rejected files and dotfiles (`.<hash>.parts`). The torrent keeps seeding from quarantine under D-21. Phase 4 renaming will apply to the link. — **Reversibility:** costly — Phase 4 builds its rename on top of the link-based hand-off.
- **D-47:** When seeding ends (D-21 share limit reached) or the user taps "Remove from list" (D-33), the torrent is removed with **`deleteFiles=true`**. That deletes only the quarantine link; the media hardlink keeps the film, so D-33's "the film is never deleted from the phone" still holds. **D-33 is amended:** deleteFiles=false becomes true, because the files now live on through the media link.
- **D-48:** If the hardlink fails (e.g. EXDEV: `DATA_ROOT` spans two filesystems), **never fall back to copy**. Log the error, keep the row in Checking, and have the doctor check at startup that quarantine and media share one filesystem.
- **D-49:** Files already in the media folders from Phases 1–2 are **left as they are**. `docs/setup.md` notes that only post-2.1 downloads are verified. No migration code.

### Pipeline trigger and states
- **D-50:** A **backend background poller** (~10 s, inside the FastAPI lifespan like the bootstrap task) finds completed Film/SerieTV torrents not yet verified. It works with no phone open and re-scans after a restart. No qBittorrent "run on completion" hook.
- **D-51:** Verification starts when the **whole torrent** completes (one trigger per torrent, not per file).
- **D-52:** **One probe at a time** (serial queue). A 10-episode pack means ~10 VM boots in sequence.
- **D-53:** New plain state **"Checking…"** (QUAR-04's "verifying") between Downloading and Ready. "Ready" only after the hand-off. **Cancel is allowed during Checking** (one confirm, as D-32) and deletes the quarantine files.
- **D-54:** Verification state must **survive a backend restart**, derived from disk and/or qBittorrent (e.g. a qBittorrent tag or a marker in `rejected/`), not only the in-memory job registry. A restart mid-check re-runs the check.

### Rejected files
- **D-55:** A failing file is **moved to `rejected/`** (outside Jellyfin's reach, owner-only, never executable) and **auto-purged after 7 days** (env-configurable, same default as D-28).
- **D-56:** The user sees a plain message on the row: **"This file didn't pass the safety check. Try another result."** (new `messages.js` entry). The row stays **24 h** like other failures (D-29) and has **no actions**.
- **D-57:** A **probe crash or timeout** gets **one retry in a fresh VM**. If the retry also fails, the file is rejected (QUAR-02).
- **D-58:** If the **runner itself is unavailable** (no `/dev/kvm`, sandbox service down), files **stay in quarantine** and the row stays in Checking. The admin log and the doctor flag it, and the check retries when the runner is back. **Never fail open, never reject because of a host fault.**
- **D-59:** **No admin override** in 2.1. Releasing a false rejection is a documented manual host step (move the file from `rejected/` into `media/<Category>`).
- **D-60:** The admin learns about rejections from a **`quarantine.rejected` audit line** (torrent name, file, reason, short probe summary) in the existing stdout trail (D-40/D-41). The doctor also reports the count of held files. No reason files on disk.

### Multi-file torrents
- **D-61:** In a **mixed pack** (e.g. 9 of 10 episodes pass), the passing files are linked into media and the failing ones moved to `rejected/`. The row shows **Ready with a note** ("1 file didn't pass the safety check"). Then the torrent is **removed at once with deleteFiles=true**: a torrent that contained a suspect file is never seeded.
- **D-62:** **Subtitles** (`.srt .ass .ssa .sub .idx`) are not probed in the VM. Text subtitles get a size cap plus a valid-text check (no binary); `.sub/.idx` get a size cap only. They move only if **at least one video from the same torrent passed**.
- **D-63:** Films: **every passing video except samples** moves (same "sample" naming rule as the D-43 main-video choice), so extras can reach Jellyfin.

### Validation rules (QUAR-03)
- **D-64:** **Duration minimum:** film main video ≥ **40 min**, each series video ≥ **10 min**. Env-configurable, no upper bound. In a film torrent the minimum applies to the **main video only**; extras must still be real videos and pass the bitrate band.
- **D-65:** **Size plausibility = bitrate band:** size / duration between ~**100 kbps** and ~**100 Mbps** (env-configurable).
- **D-66:** **Container ↔ extension, strict family map:** `.mkv` → matroska (the matroska/webm demuxer), `.mp4`/`.m4v` → mov/mp4 family, `.avi` → avi. A mismatch is rejected.
- **D-67:** **Codec:** any real video codec ffprobe recognizes. Attached-picture / cover-art streams (`disposition.attached_pic`) do not count as video. This is a safety check, not a TV-compatibility check.

### Runner (sandbox) architecture (QUAR-02, QUAR-05)
- **D-68:** The runner is a **separate compose service** (e.g. `sandbox`) with `devices: /dev/kvm`, **not privileged**, on its own internal network with **no egress**. **Research must prove `/dev/kvm` works in a container under Docker Desktop (WSL2 dev)** as well as on native Docker Engine (Ubuntu Server). If Docker Desktop cannot pass it through, document a fallback rather than redesign. — **Reversibility:** costly — compose topology, networks and infra invariant tests depend on it.
- **D-69:** **Interface:** a small HTTP API, e.g. `POST /probe {relative path}` → JSON facts. The backend sends only paths relative to the quarantine root; the runner resolves them under that root only and refuses traversal. This is the "one stable interface" of QUAR-05. — **Reversibility:** costly — the contract is what makes the sandbox swappable; changing it touches both sides and tests.
- **D-70:** **The runner returns facts, the backend judges.** The runner returns parsed ffprobe facts (format name, streams with codec type/name/disposition, duration, size, exit/timeout status). The backend applies D-64..D-67, so thresholds are unit-testable without KVM and survive a sandbox swap.
- **D-71:** **Firecracker jailer** per VM (chroot, seccomp, cgroups, unprivileged uid) inside a hardened container: cap_drop ALL plus only what the jailer needs, read-only container rootfs, quarantine mounted **read-only**. In the VM: **no network device**, the file attached **read-only**, fresh VM per file, destroyed after.
- **D-72:** VM limits default to **1 vCPU, 256 MB, 60 s** wall-clock (covers boot + probe + shutdown). Env-configurable.
- **D-73:** **Guest image:** pinned Alpine release + pinned `ffmpeg` apk (checksummed), built into a small ext4 rootfs with a tiny init that runs ffprobe, writes JSON to the console/a vsock or output device, and powers off. The guest kernel is built from a pinned source/config by a script. **Pinned Firecracker release**, downloaded checksum-verified.
- **D-74:** The kernel, rootfs and Firecracker binaries are **built into the sandbox image** by a multi-stage Dockerfile, so `docker compose build` does it all, the same on WSL2 and Ubuntu. No binaries are committed (QUAR-05).

### Testing
- **D-75:** The default test suites use a **fake runner** (no KVM). An **opt-in real-sandbox suite** (marker like the existing `-m integration` guard) runs real microVMs against generated fixtures: a real short video, a renamed executable, a truncated file, a text file, a container/extension mismatch.
- **D-76:** `scripts/smoke.py` is extended so the Blender download goes **Downloading → Checking → Ready** and the file appears under `media/<Category>`. The rejection path is covered by the D-75 fixtures, not by a live torrent.

### Claude's Discretion
- The D-28 7-day list window starts at "Ready" (after hand-off), not at download completion.
- Where the purge job runs (expected: the same backend poller), and the exact poll interval.
- How verification state is persisted (qBittorrent tags vs marker files), as long as D-54 holds.
- How ffprobe output leaves the guest (serial console, vsock, or an output block device).
- New doctor checks: `/dev/kvm` reachable by the runner, quarantine and media on one filesystem, held-file count, runner health.
- Checking-row visuals (spinner, no %), keeping large tap targets and the existing CSP.
- Audit event field names, consistent with Phase 2's format.
- Exact sample-file rule reuse from `backend/app/download/allowlist.py`.

</decisions>

- `backend/app/audit.py`: audit trail with redaction. Add `quarantine.*` events.
- `backend/app/tools/doctor.py`: admin health tool. Add the sandbox checks.
- `backend/tests/fakeqbit.py` + `backend/tests/integration/`: fake engine and opt-in real-engine pattern to mirror for the fake/real runner (D-75).
- `frontend/src/messages.js`: plain-English messages. Add the Checking and rejected texts.

### Established Patterns
- Settings from env in `backend/app/config.py` with field validators on paths (`save_path_film`, `save_path_tv`, `incomplete_path`). New paths and thresholds follow the same pattern.
- Background work starts in the FastAPI `lifespan` (`backend/app/main.py`, `bootstrap_task`).
- Infra invariants live in `infra/tests` (no published ports except web, networks, mounts). New service and networks need matching invariants.
- The browser identifies torrents by opaque ids only (D-35). No paths in responses.

### Integration Points
- qBittorrent category save paths → `quarantine/<Category>`; incomplete stays separate under `DATA_ROOT/incomplete`.
- Backend → sandbox over a new internal network; the backend needs a read-write `DATA_ROOT` mount (link, move to rejected, purge), and the sandbox a read-only quarantine mount.
- Downloads API/list: new `checking` and `rejected` states, plus the "some files didn't pass" note on Ready rows.

<specifics>
## Specific Ideas

- Production target is a KVM-capable x86_64 box (N100/N150 class) on Ubuntu Server; the dev host is WSL2 + **Docker Desktop**, where `/dev/kvm` exists in the WSL distro but passing it to containers is unverified. This is the first thing research must settle.
- The hardlink hand-off mirrors the common *arr pattern (seed from the download folder, hardlink into the library).
- Rejection text matches the tone of the existing "This video format isn't supported. Try another result."

</specifics>
