# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-23
**Depth:** standard
**Files Reviewed:** 33 (production code; test files not read)
**Status:** issues_found

## Summary

The path-safety work is solid. The lexical and `realpath` checks match in the backend and in the runner, so no path escapes between quarantine, media and rejected. The cancel-vs-handoff ordering is sound, no path or qBittorrent detail reaches the browser, the sandbox hardening matches the design, and the proxy trusts only the right-most `X-Forwarded-For` entry.

The two blockers are failure-handling bugs. One can stall the whole verifier queue. The other can silently delete good downloads when the sandbox is misrouted or misconfigured. The warnings are mostly one failure mode: a single bad torrent or a stale snapshot starves or harms others.

## Critical Issues

### CR-01: chmod 0600 on a hardlinked rejected file also locks the sandbox out of the quarantine file, which stalls the whole queue

**File:** `backend/app/quarantine/handoff.py:190` (trigger order in `backend/app/quarantine/verifier.py:405-416, 423`)

**Issue:** `link_into_rejected` makes a hardlink and then runs `os.chmod(dst, 0o600)`. A hardlink shares the inode, so the quarantine file also becomes 0600, owned by PUID. The runner runs as uid 10002 and can no longer read it.

The failure then spreads like this:
1. `vm.py:393-395` and `server.py:123-125` turn the PermissionError into a 503 `permission`.
2. The backend maps that to `RunnerUnavailable`, so `_check_video` raises `_Stop("waiting")`.
3. `run_once` (`verifier.py:156-157`) does `break`. No later torrent is checked until an admin intervenes.

The chmod happens before the torrent is deleted. Any failure after it leaves the torrent in this state:
- A later failing file's link fails, for example ENOSPC, ENAMETOOLONG, or a directory in the way. `_hand_off` then returns "held" (`verifier.py:414-416`).
- `self._outcomes.write(...)` raises OSError (`verifier.py:423`), which is not a HandoffError.

On the next tick the same torrent is re-probed and the runner reads a 0600 file. The torrent is stuck Checking, and the runner is reported as down. The same stall happens if qBittorrent's UMASK is 077, because the runner reads files as "other".

**Fix:** The 0700 rejected folders already give owner-only access, so drop the chmod on the shared inode. If a file mode is still wanted, apply it after `qbit.delete` succeeds, for example in `purge`. Also treat a runner "permission" answer as a per-file problem after N tries, not a global stop.

### CR-02: Any 400/404/409 from `SANDBOX_URL` becomes a verdict that permanently deletes the torrent

**File:** `backend/app/quarantine/verifier.py:314-317`, `backend/app/quarantine/runner_client.py:141-144` (runner side `sandbox/runner/server.py:104-106`)

**Issue:** `RunnerRefused` is turned into `_Checked(..., False, "unprobeable")`. That file lands in `failing`. `_hand_off` then links it into rejected, writes a "rejected" or "partial" outcome and calls `qbit.delete(delete_files=True)`.

Nothing separates "this file is bad" from "the host is wrong":
- The runner's unknown-route answer (`{"error":"not_found"}`, 404) is identical to its file-not-found answer.
- A sandbox bind mount that points at a stale or recreated `quarantine` directory makes every path `not_found`.
- A version mismatch, or `SANDBOX_URL` pointing at another HTTP service, gives the same result.

The backend lstat'ed the file one step earlier, so a 404 or 400 means the host and the runner disagree. It does not mean the file is bad. Yet every finished download is deleted, and the household sees "didn't pass the safety check". This breaks D-58: a host fault must never become a verdict. The doctor has no check that the runner sees the same quarantine as the backend.

**Fix:** Treat `not_found` and `invalid_path` as runner unavailability (`_Stop("waiting")`). Only `not_regular_file` stays a per-file `unprobeable`. Let the runner return a distinct code for an unknown route. Add a doctor canary that writes a file in quarantine, asks the runner to probe it, and expects an answer other than 404.

## Warnings

### WR-01: One torrent whose qBittorrent call keeps failing starves the whole queue, the purge and seeding cleanup

**File:** `backend/app/quarantine/verifier.py:146-159`

**Issue:** `check_torrent` and `_hand_off` let `QbitError` escape, for example when `delete` or `add_tags` answers 5xx for one torrent. `run_once` has no per-torrent guard, so the exception ends the tick. Candidates are sorted oldest first, so a poison torrent at the head blocks every later one on every tick, and `_purge` and `_finish_seeding` never run. A runner answer that fails `ProbeFacts.from_json` becomes `bad_answer`, a "waiting" stop that blocks the queue the same way.

**Fix:**
- Wrap each `check_torrent` in a per-torrent `try/except QbitError` that logs and continues.
- Run `_purge` and `_finish_seeding` in `finally`.
- Add a per-torrent backoff.

### WR-02: Blocking filesystem I/O (including fsync) runs on the event loop

**File:** `backend/app/quarantine/verifier.py:198-207, 273, 288-293, 394-413, 423-431`; `backend/app/quarantine/handoff.py`; `backend/app/quarantine/outcomes.py:109-141`

**Issue:** `source_path` (realpath and lstat), `_identity`, `link_into_media`, `link_into_rejected`, `OutcomeStore.get` and `OutcomeStore.write` (with `os.fsync`) are called synchronously inside `async def` methods. `_read_head`, `purge` and `load_all` are already off-loaded, so this is inconsistent. On a slow disk or a large pack it freezes login, the list and the healthcheck.

**Fix:** Run each synchronous block with `await asyncio.to_thread(...)`. Keep only the lock and the qBittorrent calls on the loop.

### WR-03: `_finish_seeding` deletes using a snapshot taken before long probes

**File:** `backend/app/quarantine/verifier.py:159, 169-209`

**Issue:** `rows` is read at the start of `run_once`, then candidates are probed (up to 2 x 60 s per video), and only then `_finish_seeding(rows)` runs. The row is not re-read inside the lock. If the same hash was removed and re-added meanwhile, the new, unverified download is deleted with `deleteFiles=true`. A stale row can also write a "ready" sidecar for a torrent that was just removed.

**Fix:** Inside the lock, call `torrents_info(hashes=torrent_hash)` again and repeat the state, tag and `in_quarantine` checks. Take `now` per row.

### WR-04: A torrent whose link keeps failing is re-probed in a VM every tick, forever

**File:** `backend/app/quarantine/verifier.py:405-416, 216-221`

**Issue:** When `_hand_off` returns "held", the torrent stays a candidate and is re-probed every 10 s before the same link fails. A permanent cause keeps the runner busy forever. Media links for the passing files are made before the failing ones are secured in rejected, so partial content sits in Jellyfin while the torrent shows Checking.

**Fix:** Remember held torrents (hash plus reason) with a backoff. Link the failing files into rejected before the passing ones go into media.

### WR-05: `makedirs` runs before the symlink check, so directories can be created outside media

**File:** `backend/app/quarantine/handoff.py:115-117`

**Issue:** `os.makedirs(dst.parent, ...)` follows symlinks and runs before `_refuse_symlinked_parents`. If an intermediate folder is a symlink, the directories are created at its target, and only then is the hand-off refused.

**Fix:** Walk the segments below `media_dir` with `lstat`, and `mkdir` one folder at a time, refusing on a symlink.

### WR-06: A transient DNS failure replaces the trusted-proxy set with an empty one

**File:** `backend/app/proxy.py:65-76`

**Issue:** `_refresh` rebuilds `trusted` from scratch. After one failed lookup, the real proxy is untrusted for up to 2 s, so every request is attributed to the proxy's address. The login throttle then counts all household members as one client, and a few wrong passwords can lock everyone out for 15 minutes.

**Fix:** Keep the previous `_trusted` set when a lookup fails, and retry sooner. Only drop an address after a successful lookup that no longer lists it.

### WR-07: Subtitles bypass the sandbox and `.sub`/`.idx` pass on size alone

**File:** `backend/app/quarantine/subtitles.py:49-50` (kind chosen in `backend/app/quarantine/rules.py:150-153`)

**Issue:** A `.sub` or `.idx` file of up to 200 MB passes without any content check, and Jellyfin hands external subtitles to ffmpeg.

**Fix:**
- Run the text check on `.idx`.
- Accept a `.sub` only when it passes the text check or starts with `00 00 01 BA`.
- Use a smaller size cap.

### WR-08: Ready outcomes are purged by the rejected retention, not by `COMPLETED_VISIBLE_DAYS`

**File:** `backend/app/quarantine/outcomes.py:181-223` (settings in `backend/app/config.py:110, 134`)

**Issue:** `purge` applies `REJECTED_RETENTION_DAYS` to every sidecar. If retention is shorter than visibility, Ready rows disappear early, and a stored outcome that a pending delete depends on can be purged.

**Fix:** Purge "ready" sidecars by `completed_visible_seconds` and "rejected" ones by `rejected_retention_seconds`. Or reject a config where retention is below visibility.

## Info

### IN-01: `rejected` root can be created with default permissions

**File:** `backend/app/quarantine/handoff.py:170-171`

**Issue:** `os.makedirs(rejected_dir.parent, exist_ok=True)` uses the umask (0755). `OutcomeStore.write` and `init-host-dirs.sh` both use 0700.

**Fix:** Create it with `mode=0o700`.

### IN-02: Purge ages a held folder by its top-level mtime only

**File:** `backend/app/quarantine/outcomes.py:209-212`

**Issue:** Re-rejecting a nested file of the same torrent does not extend retention.

**Fix:** Use the newest mtime in the tree, or the sidecar's `at`.

### IN-03: `PROBE_TIMEOUT_SECONDS` is not checked against `VM_TIMEOUT_SECONDS`

**File:** `backend/app/config.py:122`, `.env.example:107`, `sandbox/runner/vm.py:52`

**Issue:** If `VM_TIMEOUT_SECONDS` is raised above the backend's 90 s timeout, every slow file times out on the backend side and the runner is reported down. The abandoned request keeps the VM lock.

**Fix:** Document the relation, or derive the backend timeout from the VM timeout plus a margin.

### IN-04: Runner HTTP server has no socket timeout and does not drain unread bodies

**File:** `sandbox/runner/server.py:99-106, 48-51`

**Issue:** An idle connection holds a thread (`pids_limit` is 64). An early 404 on a keep-alive POST can desync the next request.

**Fix:** Set `timeout = 30` on `Handler`, and read or close the connection on early error returns.
